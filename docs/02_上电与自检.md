# 02 上电与自检

每天开工按这个顺序做，5 分钟能全部到位。**顺序不能乱**，原因见第一节末尾。

---

## 一、启动顺序（记住这个图）

```
① 配置 CAN（sudo）        bash bringup.sh can
        ↓
② 起相机（终端 A，别关）  bash bringup.sh cams      ← 它同时是 ROS master
        ↓
③ 起机械臂（终端 B）      bash bringup.sh arms 0     ← 采集模式
        ↓
④ 自检（终端 C）          bash bringup.sh check
        ↓
⑤ 开始采集              bash record_here.sh grasp_cube 0 400
```

**为什么相机必须先起**：`roslaunch astra_camera` 会顺手把 ROS master 启起来。反过来先起机械臂，相机再起会提示 master 端口被占或者两边各自起一个 master，互相看不见话题。同理，**杀掉相机 launch 会把整个 ROS 环境带走**（机械臂节点也跟着掉线）。

---

## 二、① 配置 CAN

```bash
bash ~/cobot_magic/bringup.sh can
```

需要输入 sudo 密码（脚本内部只对 CAN 配置这一步提权，不用整条命令加 sudo）。

正常输出：

```
can_left : UP, bitrate=1000000
can_right: UP, bitrate=1000000
can0     : UP, bitrate=500000
```

**验证臂真的在通信**（配置成功不代表臂通电）：

```bash
for c in can_right can_left; do
  a=$(cat /sys/class/net/$c/statistics/rx_packets); sleep 1
  b=$(cat /sys/class/net/$c/statistics/rx_packets)
  echo "$c: 1 秒 $((b-a)) 帧"
done
```

- `3000 帧/秒` 左右 → 臂已上电、CAN 通 ✓
- `0 帧/秒` → 臂没开电源，或 USB-CAN 没插好，或 CAN 没配好

---

## 三、② 起相机

```bash
bash ~/cobot_magic/bringup.sh cams      # 终端 A，用完再关
```

启动的是 `camera_ws/src/ros_astra_camera/launch/grasp_2cams.launch`，只起两路彩色（关掉深度/IR/点云，减少 USB 带宽）：

- `/camera_r` 头视，序列号 `CC1S74100TL`
- `/camera_l` 右腕，序列号 `CC1S74101HL`

验证：

```bash
timeout 6 rostopic hz /camera_r/color/image_raw   # 期望 ~30 Hz
timeout 6 rostopic hz /camera_l/color/image_raw
```

两路都要 30 Hz。如果只有 10~15 Hz，通常是 USB 带宽不够（别插在同一个 USB 3.0 hub 上）或别的程序占着相机。

---

## 四、③ 起机械臂

### 采集：mode=0

```bash
bash ~/cobot_magic/bringup.sh arms 0        # 终端 B，保持不关
```

此时**主臂要上电**（上电后从臂会跟着主臂动，这就是遥操作）。

正常标志：

```
/puppet/joint_left  : 200 Hz
/puppet/joint_right : 200 Hz
```

### 推理：mode=1

```bash
bash ~/cobot_magic/bringup.sh armstop       # 停机械臂节点，相机不动
bash ~/cobot_magic/bringup.sh arms 1        # 重新以推理模式启动
```

此时**主臂必须断电**（拔掉主臂电源）。原因见 `docs/01` 第三节：mode=1 下 `/master/joint_*` 由 `inference.py` 发布，主臂固件也在同一通道上写，会互相打架。

切回采集就是反过来：`armstop` → `arms 0` → 主臂上电。

## 五、④ 自检

```bash
bash ~/cobot_magic/bringup.sh check
```

四步输出怎么读：

| 步骤 | 正常 | 异常处理 |
|------|------|----------|
| 1. 话题检查 | 6 个话题全 ✅ | 有 ❌：对应的 roslaunch 没起，或 master 不对 |
| 2. 频率检查 | 相机 30 Hz、关节 200 Hz | 无数据 / 频率低：见 `docs/06` |
| 3. 主从对比 | 你拖动右主臂，master 明显变化，puppet 跟随，两者差 0.02~0.3 rad | master 不变 / master≡puppet：固件随动配置不对，**先别采数据** |
| 4. 结论 | —— | —— |

第 3 步是**最关键的一项**：如果 `master` 和 `puppet` 完全相等，说明录进 HDF5 的 `action` 其实是从臂实测值，训出来的策略是"恒等映射"，实机上根本不动。

## 六、常见上电问题（详见 06）

| 现象 | 原因 |
|------|------|
| 机械臂节点打印"程序自动使能超时,退出程序"后自己退出 | 5 秒内没收到 `driver_enable_status`：臂没上电，或 CAN 没报文 |
| 所有话题都没有 | ROS master 没起（相机/机械臂 launch 都没起），或相机被杀了 |
| `check` 显示 `/camera_f` 缺失 | 正常，本来就只有 2 路相机（新版脚本已不再检查它） |
| `rostopic hz` 有但数值乱跳 | USB 带宽/CPU 抢占，换 USB 口；或先停掉训练任务 |

## 七、收工

```bash
bash ~/cobot_magic/bringup.sh stop      # 停相机 + 机械臂
# 机械臂断电（主从都断）
```

**不要**用 `pkill -f ros`、`pkill -9 python` 这类大范围命令，会把别的东西一起带走。项目里所有脚本都用精确匹配，见 `docs/06` 的 pkill 陷阱一节。

---

## 八、异常恢复

出现"ROS 环境乱了"（话题半死不活、master 连不上）时，按这个顺序重来：

```bash
# 1) 全部停掉
bash ~/cobot_magic/bringup.sh stop
sleep 3

# 2) 确认没有残留
pgrep -af "roslaunch|astra_camera_node|piper_start_ms_node" | grep -v grep

# 3) 从相机开始重新起（相机 → 机械臂）
bash ~/cobot_magic/bringup.sh cams
bash ~/cobot_magic/bringup.sh arms 0
```
